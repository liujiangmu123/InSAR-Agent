# 06 · 完备性判定:照这套文档做完,能不能"完美完成任何 InSAR 全流程任务"?

> 这一份直接回答验收问题。判定基于对仓库的实测清点(11 步注册表、77 个后端端点、16 个工具、本机 70+ 个 MintPy CLI),不是主观印象。

## 0. 判定结论

**原 13 份文档(仅基线 + 工具雏形,即今 Phase 01-05/09/16 的前身)的答案是:不能。**

原计划解决的是"**把 pi 外壳接到现有内核上并跑通真实数据**"——这是必要的地基,但它只覆盖了"数据 → 速度场 → 一张主图"的主链。用户要的"分析结果、出图、预测、文档输出等全流程任务",有三类硬缺口:

| 缺口 | 性质 | 严重度 |
|---|---|---|
| A. 后端已实现的分析/出图/导出/报告能力,LLM 完全够不着(77 端点仅 22% 暴露) | **接线缺口**(不用写科学代码) | 🔴 致命 |
| B. 本机 MintPy 已装的 70+ 下游 CLI,注册表一个都没声明(升降轨分解、剖面、电离层、解缠误差、KMZ、网络图……) | **声明缺口**(需加注册表 + 引擎构建器) | 🔴 致命 |
| C. 预测/变化检测/反演桥完全没有 | **能力缺口**(需新建,但有明确边界) | 🟠 重要 |

**扩充后(Phase 01-16)的答案是:能。** 并且有边界声明——见 `04-science-capability-map.md` §6"明确不做"。

## 2. 为什么"接线缺口"是致命的

一个具体例子:后端 `report/draft.py`、`results.py`、`captions.py` 实现了**极高质量**的防幻觉报告生成——事实闭集抽取、骨架纯代码拼接、LLM 只润色、润色稿必须通过"数值双向一致 + 方法名保全 + 模拟警示保全"三重校验,任一不过就整体回退骨架。

这套东西**已经写好并有测试**,但 pi 里的 LLM 根本调不到它。结果是:用户问"帮我写方法章节",LLM 只能凭对话上下文自己编——**恰好绕过了本项目最核心的防幻觉设计**。

同理:
- `/api/timeseries-point` 已实现,但 LLM 问"这个点沉降多少"只能猜;
- `/api/export` 能出 GeoTIFF,但 LLM 说"我无法导出";
- `/api/vision-qa` 能让模型看图判质量,但没人调用;
- `/api/advise` 有确定性的下一步建议引擎,但 LLM 自由发挥。

**这不是"少做了功能",是"做好的功能被架空"。** 所以 Phase 05-08 优先级最高、成本最低、收益最大。

## 3. 为什么"声明缺口"能低成本补上

架构上的关键性质(已核对源码):

```python
# planner/plan.py:51  —— 规划器遍历注册表,不是硬编码 11 步
for sid in sorted(registry):
# runtime/executor.py:103 —— 执行器按 step_id 查注册表
cap = ctx.registry[step_id]
# loop/driver.py:222 —— 注册表可注入
self.registry = registry or REGISTRY
```

因此**新增一个科学能力 = 在 `capabilities.py` 加一条 `Capability` 声明 + 在 `engines/` 加一个 `build() → CommandPlan`**,即可自动获得:

规划 → 可行性收窄 → 指纹 → 五阶段执行 → 产物发现 → run_ok 双判定 → 质量门 → provenance → 证据阶梯 → 失效传播 → 侧栏显示 → 被 `insar_apply_change` / `insar_fork_run` 驱动

**不需要新工具、不需要改执行器、不需要改账本。** 这是本项目此前架构投资的红利,Phase 10-15 因此是"填声明"而不是"造系统"。

## 4. 三个必须先拍板的设计决策

Phase 10 开工前必须定,否则会返工:

### D1. 可选步骤怎么表达?
问题:规划器给注册表里**每一个** capability 都排一步。若把"剖面分析"直接加进注册表,每个 run 都会多出一步,而大多数 run 并不需要。

**决策:给 `Capability` 加 `group: str = "core"` 字段,规划器按 group 过滤。**
- 核心 11 步 `group="core"`(默认值,**现有声明一行都不用改**);
- 分析步骤 `group="analysis"`,id 从 20 起(12-19 预留给核心链成长);
- `_plan_methods` 加一个 `groups: tuple[str,...] = ("core",)` 过滤条件;
- 收益:**现有 11 步断言全部继续通过**(核心 run 仍恰好 11 步),零破坏。

### D2. 跨 run 分析(升降轨分解需要两个 run)怎么落账?
**决策:走"分析 run"——用 `groups=("analysis",)` 规划一个独立 run,源 run_id 作为 science 参数进入指纹。**
- 好处:完整走五阶段执行器与账本;源 run 变了 → `args_hash` 变 → 正确标脏;
- 不改数据库多父结构,源 run 记在 `intent` 与 step params 里。

### D3. 校正链补齐是加步骤还是加方法?
**决策:加方法与参数,不加步骤。** MintPy 的 `correct_unwrap_error` / `correct_ionosphere` **本来就落在 `smallbaselineApp --start/--end` 的现有区间内**(第 7 步 `load_data..invert_network`、第 8 步 `correct_LOD..reference_date`),只是 `engines/mintpy.py` 的 `_CFG_TEMPLATE` 没渲染对应配置键。补齐 = 扩模板 + 加 `Method`/`Param` 声明。

## 5. 优先级与最小可交付线

| 优先级 | Phase | 不做的后果 |
|---|---|---|
| **P0 必须** | 01-04(基座) | pi 跑不起来 / 连不上真实引擎 |
| **P0 必须** | 05-08(工具面补全) | 已建成的分析·出图·导出·报告能力被架空,Agent 只会跑流水线不会交付 |
| **P1 强烈建议** | 10-12(后处理 / 校正 / 出图) | 无法回答"沉降多少、哪里在动、给我看图",科学价值大打折扣 |
| **P2 建议** | 13-14(预测 / 反演桥) | 无法预测与深度解译,但主流程完整 |
| **P2 建议** | 15(场景包) | 每次都要人工配参数,自动化程度低 |
| **P0 必须** | 09、16(日志 / 收口验收) | 无法证明"确实做完了" |

**最小可交付线 = Phase 01-09 + 16**:此时 Agent 能用真实数据跑完整链、查点位、出图看图、导出 GIS 产品、生成方法与结果章节、打包复现包——已经是一个可用的 InSAR 全流程 Agent。10-15 是把"可用"推到"完备"。

## 6. 判定复核方式

执行完全部 Phase 后,用 `41-appendix-final-checklist.md` 逐条打勾。其中最能证明"完备"的三条端到端验收:

1. **真实数据全链**:用 `workspace/realtest` 的 Ridgecrest 数据,在 pi 里用自然语言走完"规划 → 执行 → 查点位 → 出图 → 看图质检 → 导出 GeoTIFF → 生成结果章节 → 打包复现包",全程只用 `insar_*` 工具;
2. **分析 run**:对同一区域的升降轨结果做分解,得到垂直与东西向速度场并出图,且 provenance 能追到两个源 run;
3. **可复现**:导出的复现包在另一台机器上按 `run.sh` 重跑,产物 sha256 与 MANIFEST 一致。

三条都过 = 完备性判定通过。
