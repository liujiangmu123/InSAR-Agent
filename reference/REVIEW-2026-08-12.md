## 第一部分 · 缺陷清单

### P1-1 服务重启 reattach 形同虚设,且把可恢复 run 误置 failed

- **位置**:`loop/driver.py:256-264`(`execute` 待跑集合)与 `loop/driver.py:409-428`(`resume`)。
- **问题**:`execute()` 计算待跑步骤时,集合是
  `state in ("pending","stale","interrupted","orphaned")` —— **不含 `"running"`**。
  而活作业在执行期间恰恰是 `state=running`(stage 停在 `LAUNCHED`,`RUNNING` 阶段只在
  作业结束后才置位)。`resume()` 先按 `state=="running" and stage in (PREPARED,LAUNCHED,RUNNING)`
  找到 live 步骤、发出 `reattach` 事件,然后调 `execute()` —— 但该 live 步骤被待跑集合过滤掉,
  **永远不会调用 `execute_step` 去接回**。执行器本身支持 reattach(stage 守卫在 `LAUNCHED`
  会进入 `RUNNING` 块续读日志,`test_reattach_after_service_restart` 已证明),缺陷只在
  driver 的步骤选择。
- **触发场景**:真实服务重启(宿主进程被杀但 detached wrapper 存活)后调 `POST /api/resume`。
  live 步骤被跳过;其下游 `pending` 步骤反而进入待跑集合,在 `PREPARED` 阶段
  `find_artifact` 找不到 live 步骤尚未产出的输入 → `contract_broken` → 整个 run 置 `failed`。
  即:reattach 设计目标场景反而破坏 run 状态。
- **验证**:`test_admin_control.py::test_cancel_intent_survives_restart` 只覆盖
  `resume→读到 cancel_requested→提前收尾` 这条早退路径;真正的「live 作业经 resume 接回」
  路径无任何测试覆盖。
- **建议修法**:`execute()` 待跑集合纳入 `state=="running"` 且 `stage != "VERIFIED"` 的步骤
  (它们通过 stage 守卫天然 reattach),并且**不要**对这些步骤 `reset_step_for_rerun`
  (只 reset stale/interrupted/orphaned)。`topo_order` 已保证 live 步骤排在其下游之前。

### P1-2 provenance 的 interventions 跨 run 污染

- **位置**:`core/ledger.py:58-63`。
- **问题**:
  ```python
  for a in store.db.query(
      "SELECT * FROM pending_actions WHERE consumed_at IS NOT NULL ORDER BY id")
  ```
  查询没有任何 run/session 过滤 —— 因为 `pending_actions` 表(`core/schema.sql:134-143`)
  根本没有 `run_id` 列。导出任一 run 的 provenance 时,`interventions` 字段会包含
  **数据库里所有历史 run/会话** 已消费的干预动作。对一个「以 provenance 完整性为核心卖点」
  的系统,这是溯源正确性缺陷:账本把别的 run 的操作算到本 run 头上。
- **触发场景**:同一 `INSAR_HOME` 下先后跑过多个 run(常态),第二个 run 的
  `provenance.json` / `GET /api/provenance` 会带上第一个 run 的全部干预。
- **建议修法**:给 `pending_actions` 增列 `run_id`(或 `session_id`),`push_action` 落库时写入;
  `export_provenance` 用 `WHERE run_id=? AND consumed_at IS NOT NULL` 过滤。属 schema 变更,
  可复用 `core/db.py` 现成的 `_COLUMN_MIGRATIONS` 机制补列(旧库 `run_id` 置 NULL)。

### P1-3 复用既有 run 时 next_run 干预被静默丢弃

- **位置**:`loop/driver.py:152-179`。
- **问题**:`turn()` 开头无条件消费 `next_run` 队列,累积成 `overrides` 并
  `store.consume_action(...)`(动作标记已消费,不可逆);随后如果
  `latest_run` 命中同场景且状态在一个很宽的集合里,直接 `run_id = latest["run_id"]`
  复用旧 run,**`overrides` 只传给 `make_plan`,复用分支根本不接它**。于是排队的
  「下次规划时把第 9 步换成 exponential」被消费掉却没落到任何步骤上。
- **触发场景**:第一次 `turn` 建了 run;之后用户排队 `deliver_as=next_run` 的 SET_METHOD,
  再 `turn`(同场景)→ 命中复用分支 → 干预丢失。这几乎是 next_run 的主用例,等于该
  投递语义在常见路径下失效,违背 absorb-E4「next_run 在下一次规划生效」的承诺。
- **建议修法**:复用分支里也要应用 `overrides`(对既有步骤走 `stale.apply_change` 落配置与级联标脏);
  或在存在未消费 `next_run` 干预时强制重规划而非复用。至少:命中复用时**不要**提前消费
  next_run 队列(留到真正规划时再消费)。

### P1-4 步级排他锁 / 资源仲裁未接线,并发执行崩断

- **位置**:`loop/driver.py:254-302`(execute 主循环)、`core/store.py:595-626`(leases)、
  `runtime/executor.py:272`(只 `except StepExecutionError`)。
- **问题**:AGENT-DESIGN §4.11 明确「同一产物并发写 → 步级排他锁,第二次直接拒绝」,
  `store` 也实现了 `acquire_lease/heartbeat_lease/release_lease` + `leases` 表。但**全项目
  没有任何地方调用 `acquire_lease`**(grep 仅命中定义与 `test_store.py`)。driver/executor
  跑步骤前不取锁,也没有 §4.11 的 CPU/内存/IO 资源池调度。并发两次 `POST /api/pipeline`
  同一 session(用户点两下运行、或 pipeline 与 resume 并行)→ 两个 `execute()` 协程都推进
  同一步 → `store.advance` 的 CAS 让输者抛 `StageConflict`;而 `execute_step` 只捕获
  `StepExecutionError`,`StageConflict` 直接穿透 `exec_task.result()`,回合的 NDJSON 流
  中途抛异常崩断(见 P2-6),并可能重复 `launch` 命令。
- **触发场景**:任何对同一 run 的并发 execute(前端重复点击、resume 撞上进行中的 pipeline)。
- **建议修法**:`execute()` 进入前 `acquire_lease(f"run:{run_id}", holder=...)`,拿不到直接
  返回「已有执行在进行」的 note;正常/异常退出 `release_lease`,长任务期间 `heartbeat_lease`。
  同时在 `execute_step` 或 driver 层捕获 `StageConflict` 并转成结构化 note(输者自停,不崩流)。

### P1-5 run_ok 的 not_all_nan 对真实 h5 产物失效

- **位置**:`audit/runok.py:61-74`(`_nan_fraction`),被 capability 7/9 的
  `RunOkCheck("not_all_nan", ...)` 引用(`registry/capabilities.py:233,312`)。
- **问题**:`_nan_fraction` 只处理 `.npy`,其余后缀返回 `None`;`not_all_nan` 分支拿到
  `None` 时返回 `CheckResult(..., True, "warn", ...)`。而第 7/9 步的产物是
  `timeseries.h5`/`velocity.h5`(content 档 h5)——**永远解析不了 → 永远 warn 放行**。
  即「MintPy 可能成功输出全 NaN 时序」这一 run_ok 双判定的立身场景,恰恰守不住。
- **触发场景**:真实 MintPy 反演产出全 NaN 的 `velocity.h5`(参考点选在无效区等)→
  `not_all_nan` 只 warn,run_ok 仍判 pass,坏结果流入下游与报告。
- **现状**:README「当前边界」已诚实声明此项待接 h5py 宿主校验。属**已知**缺口,但仍是 P1。
- **建议修法**:`_nan_fraction` 增加 h5 分支(`h5py` 读主数据集算 `isnan` 占比),
  h5py 缺失时再降级 warn;或把 h5 校验并入 `audit/verify.py` 的重解析路径统一处理。

### P2-1 `new_run_id` 用本地时间,provenance 用 UTC —— 时间戳不一致

- **位置**:`core/store.py:34-37`(`time.strftime("%Y%m%dT%H%M%S")`,本地时区)
  vs `core/ledger.py:84`(`time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime())`,UTC)。
- **问题**:`run_id` 前缀是**本地时间**,provenance 的 `generated_at_utc` 是 UTC,
  其余时间戳(`created_at`/`started_at`/…)是 `time.time()` epoch。跨时区/夏令时协作或
  排序 run_id 时,run_id 的时间前缀与账本 UTC 对不上。run_id 有 uuid 后缀不影响唯一性,
  但作为「可读时间线索」会误导。
- **建议修法**:run_id 前缀统一改 `time.gmtime()`(UTC),或在文档明确 run_id 时间为本地、
  一切对外时间戳为 UTC。属横切面「时区一致性」问题,建议全库统一 UTC。

### P2-2 裸/宽 except 吞异常的几处

- **位置**:`api/app.py:183`(`except Exception: pass`,WSL 探测合并)、
  `runtime/probe.py:82,103,154`、`audit/runok.py:73`(`_nan_fraction` 的 `except Exception`)。
- **问题**:多为「尽力探测,失败静默」的合理降级,但 `except Exception: pass` 粒度过宽,
  会连同 `KeyboardInterrupt` 之外的编程错误(拼写、类型)一起吞掉,排障困难。
  尤其 `runok._nan_fraction` 的 `except Exception: return None` 会把「产物存在但 h5 读损坏」
  与「格式不支持」混为一谈,双双降级 warn(叠加 P1-5)。
- **建议修法**:收窄到预期异常(`OSError`/`subprocess.SubprocessError`/`ImportError`/
  `ValueError`),或至少记一条 debug 级 trace,不静默。

### P2-3 provenance/账本导出的原子写不清理临时文件

- **位置**:`core/ledger.py:110-118`、`report/script.py:55-63`、`runtime/render.py:20-27`。
- **问题**:都走 `tmp.write_text()` + `os.replace()`(原子,✓),但**写 tmp 与 replace 之间抛异常**
  (磁盘满/编码错)会残留 `*.tmp` / `*.json.tmp`,无 try/finally 清理。`render_plan_files`
  还对同名目标用固定 `.tmp` 名,理论上并发渲染同一文件会撞 tmp。
- **建议修法**:`try: write+replace except: unlink(tmp); raise`(可参照 `setup_router._atomic_write_json`
  已有的正确写法)。属健壮性,非正确性。

### P2-4 `find_artifact` 祖先链深度硬上限 32

- **位置**:`core/store.py:483-494`。
- **问题**:fork 链沿 `parent_run_id` 回溯查产物,`for _ in range(32)` 防环;超过 32 层
  fork 后祖先产物**静默返回 None**,表现为「产物缺失 → contract_broken」,而非真正缺失。
- **建议修法**:32 层是防环上限,正常够用;但触顶时应区分「疑似环/超深」与「真缺失」,
  记一条 warning,避免误报成契约破坏。

### P2-5 `log_absent` 全量读日志进内存

- **位置**:`audit/runok.py:105-112`。
- **问题**:`log_path.read_text(...)` 一次性读入整个 `job.log` 再跑正则。长任务日志可达
  数百 MB,VERIFIED 阶段这一步会瞬时吃满内存。`stream.py` 的增量读设计就是为避免这个,
  但 run_ok 校验又全量读回来了。
- **建议修法**:按块流式扫描或只读尾部 N MB(与 `api/app.py:/api/logs` 的 tail 策略一致)。

### P2-6 NDJSON 回合流中途异常无收尾

- **位置**:`api/app.py:109-113`(`ndjson` 包装器)。
- **问题**:`async for event in agen: yield ...`,若 driver 协程中途抛异常(如 P1-4 的
  `StageConflict`、P1-1 的 `contract_broken` 传播),异常在 `StreamingResponse` 生成器里抛出,
  客户端收到**截断的 NDJSON**,拿不到终态事件,违背 §2「过程与结果走事件流」的闭合承诺。
- **建议修法**:`ndjson` 的 `gen()` 包 `try/except`,异常时补发一条
  `{"t":"note","tone":"bad","text": ...}` 再正常结束流。

### P2-7 `drivers` 字典在线程池下的竞态

- **位置**:`api/app.py:100-107`(`driver_of`)。
- **问题**:FastAPI 同步端点在线程池执行;`if session_id not in drivers: drivers[...] = Driver(...)`
  非原子,两个并发首次请求同一 session 可能各建一个 Driver(各自 EventBus/probe)。
  影响:重复探测、`/api/events` 订阅到与实际执行不同的 bus 而收不到事件。
- **建议修法**:`driver_of` 加锁(`threading.Lock`),或用 `dict.setdefault` + 幂等构造。

### P2-8 subprocess 参数注入面(当前低风险,属防御纵深)

- **位置**:`runtime/wsl.py:100-105`(`prepare` 把 `plan.shell_line` **原样**写进 `cmd.sh`)、
  `runtime/jobs.py:83-85`(同)、各 `engines/*.py` 用 f-string 拼 bash 脚本。
- **问题**:未发现 `shell=True`;跨边界命令走 `wsl.exe ... --exec bash -lc <script>` 且
  env 值都过了 `shell_quote`,argv 也都是列表 —— **当前无实际注入**。但 `cmd.sh` 里
  `line = plan.shell_line` 是**逐字**写入的:今天各引擎的 `shell_line` 用的是常量步骤区间
  (如 isce2 的 start/end 来自常量表、mintpy 的 cfg 名固定),所以安全;一旦将来某引擎把
  用户可控路径/参数插进 `shell_line` 而不加引号,即成注入点。`engines/snaphu.py:28-37`
  已经在 bash 脚本里 f-string 插 `min_coh`(科学参数,类型 number,低危)。
- **建议修法**:确立并文档化不变量「`shell_line` 只能由受控常量拼接,一切外部值必须
  `shell_quote`」;或干脆废弃 `shell_line` 逐字通道,统一由 `argv` + `shell_quote` 生成。

### P2-9 证据阶梯 `capped()` 死分支

- **位置**:`audit/ladder.py:68-72`。
- **问题**:`if incomplete or not steps:` 命中时返回的三元表达式
  `capped(...) if not incomplete and steps else EvidenceResult(...)`,`not incomplete` 与
  进入条件矛盾,`capped(...)` 分支不可达。逻辑上无害(未完成本就返回 runnable=0,封顶到
  runnable 无意义),但属死代码/可读性坑。
- **建议修法**:直接返回未封顶的 `EvidenceResult("runnable", 0, reasons, ceiling=..., ...)`。

### P2-10 `executor` 完成态推进未带 CAS

- **位置**:`runtime/executor.py:184-189`(`out.kind == "finished"` 后
  `store.advance(run_id, step_id, "RUNNING", exit_code=...)` 无 `expect_stage`)。
- **问题**:执行器多数推进未用 `expect_stage` 做 CAS(§4.9/absorb-E6 强调外部终结竞争时输者自停)。
  正常单进程无碍;但与 P1-4(无锁并发)叠加时,缺 CAS 会放大竞态。`admin_router.terminate_step`
  一侧做了 CAS,执行器一侧多数没做,保护是单向的。
- **建议修法**:接线并发锁后,执行器关键推进也带 `expect_stage`,双向 CAS 才闭合。

### 横切面排查结论(逐项)

- **SQL 注入**:无。全部查询用 `?` 参数化;`advance/mark_step` 拼接的是**列名**且来自
  开发者固定 kwargs(`config_hash`/`exit_code`/`qa`…),非用户输入。✓
- **subprocess 注入**:见 P2-8,当前无实际注入(argv 列表 + `shell_quote` + `bash -lc` 传脚本)。
- **路径分隔符 Windows/WSL**:`executor` 落库前 `.replace("\\","/")`(✓);`wsl._to_posix`
  依赖字符串里含 `wsl.localhost` 解析(`runtime/wsl.py:161-168`),较脆,建议加断言/测试。
- **时区**:见 P2-1,run_id 本地时间 vs 账本 UTC 不一致。
- **裸 except**:见 P2-2。
- **并发共享可变状态**:`Driver._tokens`/`drivers` 均在单事件循环或线程池;`drivers` 有竞态(P2-7);
  DB 用单连接 + RLock 串行化(正确但牺牲吞吐)。
- **原子写**:provenance/run.sh/render/settings 都用 tmp+replace(✓),仅缺异常清理(P2-3)。
