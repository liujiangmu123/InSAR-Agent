## 2. P1(已修复):`base_url` 未校验 → SSRF/LFI

**位置:** `src/insar_agent/api/llm_router.py`(`post_config` / `post_models`)。

**问题:** `save_llm_config` 与 `/models` 对 `base_url` 不做 scheme 校验;
provider(`brain/provider.py`)用 `urllib.request.urlopen` 出网。实测:

```
urlopen("file:///<dir>/models") → 读取本地文件 <dir>/models(探针 FILE scheme readable: True)
```

`/api/llm/models` 的 `base_url` 来自请求体、未落盘即直接出网,配合 `+ "/models"`
拼接,`file://` 可读本机文件(constrained 到以 `/models`、`/chat/completions` 结尾
的路径),`http://` 可探测内网/云元数据端点。本应用无鉴权、信任边界为回环,
浏览器侧恶意页面(CSRF/DNS rebinding 形态)可驱动此面。

**修复(唯一产品代码改动点,净增 16 行):** 出网地址 scheme 白名单,拒绝
非 `http/https`。落在 API 边界(与仓库"校验挡在 app 层"一致):

```python
_ALLOWED_URL_SCHEMES = ("http", "https")

def _require_safe_base_url(base_url: str | None) -> None:
    s = (base_url or "").strip()
    if s and urlsplit(s).scheme.lower() not in _ALLOWED_URL_SCHEMES:
        raise HTTPException(400, "base_url 仅支持 http/https(拒绝 file:// 等非 HTTP 协议)")
```

`post_config`(落盘前)与 `post_models`(直传 `base_url` 出网前)各调用一次。
`/test` 只消费已落盘配置(落盘时已校验),env 变量路由属运维/CI 可信面,不改。

**验证:** `test_llm_base_url_ssrf_schemes_rejected_before_egress` —— `file://` /
`javascript:` / `ftp://` / `gopher://` 在 config 与 models 均 400 且**全程零出网**
(list_models 未被调用);`http/https`(含内网 IP)照常放行。

## 3. P2 发现(可用性,非安全;不在许可修改范围,留待后续)

### 3.1 诊断包并发生成的命名竞态

**位置:** `src/insar_agent/report/diagbundle.py`(`_zip_name` + `build_diag_bundle`)。

`_zip_name` 用 `diag-<秒级UTC>.zip`,撞名补 `-N`,但"检查存在 → 写文件"两步
非原子。8 路并发探针实测:8 次成功仅产出 **6 个不同文件**——两对线程算得同名、
同写同一路径,后者覆盖前者。Windows 上更极端时两个 `zipfile.ZipFile(path, "w")`
同刻打开同一路径可能触发共享冲突 → 该请求 500。

**影响:** 并发点"一键诊断"时个别包被静默覆盖 / 个别请求 500;对诊断工具是
低severity 可用性问题,不泄漏、不越界(zip 恒落在 `diagnostics/` 内)。

**建议(未实施):** `_zip_name` 后缀改用进程内计数 + `uuid` 短后缀,或用
`tempfile.mkstemp(dir=out_dir, prefix="diag-", suffix=".zip")` 以 `O_EXCL` 原子占名
(注意保持文件名仍落在下载白名单 `^diag-[0-9TZ-]+\.zip$` 内)。

**验证:** `test_diagnostics_concurrent_generation_safe` —— 断言安全不变量恒成立
(200 的响应必为 `diagnostics/` 内合法 zip),对可用性上的 500 记录而不判失败。

### 3.2 并发写 `llm.json` 的 `os.replace` Windows 争用

**位置:** `src/insar_agent/core/fsio.py`(`atomic_write_text`,经 `POST /api/llm/config` 触发)。

`atomic_write_text` 的文档声称"并发写同一目标互不相踩,后完成者胜"。实测
(8 路并发 `POST /config`)Windows 下 `os.replace(tmp, target)` 在目标被另一线程
的 replace 争用时抛 `PermissionError [WinError 5] 拒绝访问` → 该请求 500。

**影响:** 并发配置写(多标签页/多窗口同刻保存)个别 500。**安全属性不受影响:**
`llm.json` 始终是合法 JSON、`api_key` 合并不丢、失败分支清理 tmp 无残留(均已断言)。
severity 低(配置写是人工低频动作)。这是共享工具 `fsio` 的既有并发局限,非
r3 新增面自身缺陷。

**建议(未实施,属共享工具):** `os.replace` 包一层短重试(WinError 5 退避重试
数次),或对同一目标加进程内写锁。

**验证:** `test_llm_config_concurrent_writes_atomic_no_tmp_residue` —— 断言合法
JSON / key 不丢 / 无 tmp 残留;对 `PermissionError` 记录而不判失败。

### 4.1 残留(已评估接受):scheme 白名单不拦内网/元数据 IP

§2 的修复只挡协议(`file://` 等),不拦 `http://169.254.169.254` /
`http://10.x` 等内网地址 —— 本应用是本地单用户形态,内网 LLM 中转网关是**正当
配置**,一刀切拦 RFC1918 会误伤真实部署。任务要求的"最小防护"即 scheme 白名单,
"非回环内网地址警告注记"为可选项;权衡后不实施硬拦,仅在此声明。若未来对外
暴露(绑非回环,`resolve_bind_host` 已告警),建议叠加内网地址告警或
opt-in 拦截。
