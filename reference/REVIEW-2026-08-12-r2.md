## 第一部分 · P1 详情

### P1-1r2 显式重跑 failed 步骤 → 执行回合裸崩,run 遗留 running

- **位置**:`loop/driver.py:344-346`(复位名单只有 stale/interrupted/orphaned,
  **不含 failed**)、`runtime/executor.py:98-101`(failed/interrupted/orphaned
  状态检查在 `try:` 块**之外**,直接 `raise StepExecutionError`)、
  `loop/driver.py:413`(`exec_task.result()` 无任何异常处理)、
  `prototype/js/app.js:844-853`(`resumeRun()` 取 `workSummary().all`,其中
  resume 桶**包含 failed** 步骤,直接 `run(ids)` 发起显式列表执行)。
- **问题**:三层各自"合理"叠成崩溃链 —— 前端失败卡的「从断点继续」(本波
  P2-003 新特性)会把 failed 步骤 id 发进 `POST /api/pipeline step_ids`;driver
  的显式分支只防御 skipped、不复位 failed;executor 对 failed 状态的防御是
  **裸抛**(设计注释说"重跑由 driver 先 reset",但 driver 没做);异常穿透
  `exec_task.result()` → 生成器中断 → `ndjson` 兜底一条「服务内部错误」note。
  更糟:`_execute_run` 开头已 `set_run_status(run_id, "running")`,异常路径
  没有任何状态 reconcile → run 永久停在 status=running,租约释放后 60s 内
  重试还会被"运行锁被占用"拒绝。
- **触发场景**:任一步骤失败(计算失败或 gate_stop 均标 state=failed)→
  用户点失败卡上的「从断点继续」按钮(该按钮正是为此场景设计的)→ 回合
  秒崩,UI 只见「服务内部错误,回合中止」,run 状态僵死。这是失败恢复的
  **主流程**,不是长尾。
- **验证缺口**:`test_driver_matrix` 的模拟链全部成功,随机冒烟里 failed 状态
  不可达(KILL 产生 interrupted);无任何测试覆盖「显式列表含 failed 步骤」。
- **建议修法**(三选一即可解崩溃,建议全做):
  1. driver 显式分支把 failed 也纳入 `reset_step_for_rerun`(用户显式指名
     = 同意重试,语义与前端「从断点继续」一致);
  2. executor 入口的终态检查改为返回 `StepResult("failed", ...)` 而非裸抛
     (与其余失败路径的结构化收尾一致);
  3. driver 对 `exec_task.result()` 包一层 `except StepExecutionError` →
     mark failed + 结构化 note + `set_run_status("failed")`,回合流不断。

### P1-2r2 空待跑集合直接收尾为 done —— 失败/拦停状态可被"洗白"

- **位置**:`loop/driver.py:328-346`(待跑集合构造与 skipped 剔除)、
  `loop/driver.py:477-498`(for 循环后无条件走 verify → provenance →
  `set_run_status(run_id, "done")` → result/report 事件)、
  `api/app.py:336`(`if body.step_ids:` —— **空列表**跳过一切校验)。
- **问题**:主循环结束后的收尾不检查「是否还有未完成步骤」。三条路径都能
  让 for 循环零迭代直达收尾:
  - (a) `POST /api/pipeline {"step_ids": []}`:空列表是合法 pydantic 值,
    `if body.step_ids:` 为假跳过校验,driver 拿到 `[]`;
  - (b) 显式列表全是 skipped 步骤:本波新增的 skipped 防御把它们全部剔除
    (`driver.py:336-342`),剩下空列表 —— 即"防御成功"的直接后果是把 run
    标成 done;
  - (c) run 在**尾部步骤**失败(如第 11 步质检 gate_stop → state=failed,
    run status=failed):重跑(无 step_ids)时 failed 不入待跑集合、其余全
    done → 空集合 → 收尾。**质量门拦停的 run 再点一次"运行"就翻绿**:
    status=done + result/report 事件 + UI 完成态。provenance 里 `qa.status`
    仍是 fail、证据停在 runnable(账本诚实),但 run 状态与前端呈现说谎。
- **触发场景**:(c) 最真实 —— gate_stop 后用户重试是本能操作;(b) 由前端
  状态镜像失败(`syncStepsFromServer` catch 后保持本地旧态)时自然发生。
- **连带**:`tests/test_driver_matrix.py:233` 的 `assert_store_consistent`
  明确允许 done run 含 pending/stale 步骤 —— 把这个可疑语义**固化进了不变量**,
  修复时要同步收紧测试。
- **建议修法**:收尾前检查
  `any(s.state not in ("done", "skipped") for s in store.load_steps(run_id))`
  → 有剩余则不置 done、不发 result/report,发一条 note 说明「N 步未完成
  (含 failed 需 RESET)」;API 层对显式空列表直接 400。

### P1-3r2 NULL 归属动作的跨会话/跨 run 互吞残余

- **位置**:`api/app.py:412-420`(会话尚无 run 时 `resolve_run` 返回 None,
  `push_action(..., run_id=None)` 照常入队)、`core/store.py:552-571`
  (`due_actions` 对 `run_id IS NULL` 行**任何 run 都可见**,注释称"兼容旧数据
  与未接线的入队方")、`loop/driver.py:181-195`(turn 消费 next_run 时无 run
  过滤,仅当 `action["run_id"]` 非空才做会话归属检查 —— NULL 行直接落入消费)。
- **问题**:#10(跨 run 互吞)的修复以「行都带 run_id」为前提,但 API 今天
  仍会**制造新的 NULL 行**:会话在第一个 run 规划出来之前排队的任何动作
  (`next_run` 预约首次规划正是自然用例)归属为 NULL。后果:
  - 会话 A 预约 next_run SET_METHOD → 会话 B 先 turn → B 消费并把 A 的覆写
    应用进 B 的计划(A 的预约蒸发,B 得到没要过的方法);
  - NULL 的 steer/KILL 会被**任意会话的任意 run** 的执行回合消费 ——
    NULL KILL 等于"杀掉全库下一个跑起来的 run"。
- **触发场景**:多会话共用一个服务实例(桌面版就是);会话新建后先排干预
  再规划,顺序完全合法。
- **建议修法**:`pending_actions` 增列 `session_id`(迁移机制现成),入队时
  必填;`due_actions`/turn 消费对 NULL run 行按 session 过滤;或干脆拒绝
  「无 run 可绑」的入队(400「先规划再预约」)。旧 NULL 行的兼容窗口应设
  截止:一次性迁移后收紧为「无归属不消费」。

### P1-4r2 崩溃窗口认领不比对 argv → 配置-产物错配

- **位置**:`runtime/executor.py:141-151`(`latest_unsettled_command` 认领:
  只要旧作业目录存在且 `state != "unknown"` 就认领,**不比对 argv**)、对照
  `core/store.py:407-425`(`reserve_command` 重入侧**按 argv 匹配**才复用行,
  两端不对称)。
- **问题**:认领机制的本意是「崩溃在 launch 与 advance 之间时不重复启动」,
  隐含前提是命令没变。但下述序列打破前提:
  1. 步骤以方法 A 启动;取消时宽限超时(`cancel_and_wait` 返回 `exit_code=None`
     → `mark_step interrupted` 但**命令未结算**,`stream.py:131`);
  2. 作业其实随后自行跑完(wrapper 写了 rc,甚至 rc=0);
  3. 用户改方法/参数(steer SET_METHOD → `set_step_config` 改配置,状态
     interrupted → 重跑时被 reset,stage 回 PENDING);
  4. 重跑:PREPARED 用**新方法**渲染;LAUNCHED 块查到旧未结算命令行 →
     旧 job_dir 状态为 finished(≠unknown)→ **认领** → 新命令根本不启动,
     旧方法 A 的产物在 COLLECTED 被指纹入账、VERIFIED 通过(rc=0 时)——
     **步骤配置写着方法 B,产物出自方法 A**,账本与磁盘一起错。
  rc≠0 时表现为「方法 B 失败,退出码却来自方法 A 的旧作业」,误导分诊。
- **触发场景**:取消宽限超时(不可杀窗口、重 IO)+ 改参重试 —— 交互式调参
  的常见节奏;或 crash 后 resume 前用户先改了配置。
- **建议修法**:认领条件补 `existing["argv"] == json.dumps(plan.argv)`;
  argv 不匹配的未结算行合成结算(-255,注明 superseded)后走全新
  reserve+launch。同时补一致性:`reserve_command` 新插时把同 (run,step) 的
  其它未结算行也合成结算,否则账本残留永久"假在途"(见 P2-9r2)。

### P1-5r2 续租失败被忽略,接管后双执行器并行

- **位置**:`loop/driver.py:403-405` ——
  `store.acquire_lease(lease, holder, ...)` 的返回值直接丢弃。
- **问题**:租约的接管语义(`core/store.py:651-656`:心跳超过 stale_after
  即可被抢)设计给「崩溃回合」,但判定崩溃的唯一依据是心跳停更。原回合若
  只是**挂起**(宿主睡眠/休眠、WSL 阻塞 IO、长 GC、调试断点)超过 60s:
  resume/新 execute 接管成功;原回合醒来后续租返回 False —— 代码不看返回值,
  继续推进步骤。此时两个执行回合同时驱动同一 run:重复 launch、交错
  advance(executor 多数推进无 `expect_stage`,上轮 P2-10 仍开放,连
  StageConflict 这道最后防线都常常不触发)。
- **触发场景**:笔记本合盖睡眠中断执行,醒来前后用户点了 resume;或 WSL
  9p 卡死 >60s 后恢复。
- **建议修法**:续租失败 → 立即 note「运行锁已被接管,本回合终止」并
  return(不再收尾覆写状态);收尾阶段(verify/provenance,`driver.py:477-498`
  期间无任何续租)同样先确认仍持锁再写终态。

## 第二部分 · P2 详情

### P2-1r2 `execute()` finally 的异常序:release_lease 抛错 → keepalive 泄漏

- **位置**:`loop/driver.py:302-307`。
- **问题**:`finally` 里先 `store.release_lease()`(一次 DB 写,busy/锁超时
  可抛 `sqlite3.OperationalError`)再 `_release_run_backends()`。前者抛错则
  后者不执行:本 run 的 `wsl.exe sleep infinity` 保活进程全部泄漏(WSL P2
  释放钩子被跳过),且原始业务异常被顶替。
- **建议修法**:两个释放各自 try/except 包裹(`_release_run_backends`
  内部已经是,补 release_lease 一侧),顺序不重要,都必须执行。

### P2-2r2 回合生成器无 exec_task 收尾(GeneratorExit 接缝)

- **位置**:`loop/driver.py:389-413`(detail 队列泵)。
- **问题**:`_execute_run` 在 `yield` 点收到 GeneratorExit(服务关停时回合
  泵任务被取消、resume 内层生成器被提前关闭、GC 兜底 aclose)时:
  `exec_task` 无 try/finally 保护 —— 既不取消也不等待。后果链:
  (a) `execute()` 的 finally 立即释放租约,而 exec_task 还在后台推进该步骤
  → 运行锁保护的"单飞"被打破,新回合可入场与孤儿任务竞争(撞 StageConflict
  或双 launch);(b) exec_task 若抛错永远无人 retrieve(asyncio 警告噪音);
  (c) 无界 `detail` 队列继续堆积事件。另外 `api/app.py:189-213` 的响应生成器
  被客户端断开后,泵任务把整个回合的 NDJSON 行堆进**无界** `queue` ——
  长任务(小时级、日志滚动)下是可观的内存滞留。
- **建议修法**:`_execute_run` 的泵循环包 try/finally:GeneratorExit 时
  `exec_task.cancel()` + 吞尾(或按「run 归服务端」语义改为 detach 且**不**
  释放租约直至 exec_task 真正结束);`ndjson` 的 queue 设 maxsize 并在响应
  生成器退出后停止入队。

### P2-3r2 StageConflict 仍无人捕获(上轮 P1-4 的后半未落地)

- **位置**:`runtime/executor.py:177/209/253/283`(advance 均无 expect_stage,
  上轮 P2-10)、`loop/driver.py:413`(不捕获)、`api/admin_router.py:41-104`
  (终结者一侧 CAS 齐全,保护单向)。
- **问题**:租约挡住了「两个 execute 并发」,但 admin 外部终结与活跃执行器
  的竞争仍在:admin CAS 赢 → 执行器随后 advance/mark 抛 StageConflict →
  未捕获 → 回合崩流(与 P1-1r2 同一条「异常穿透 + run 遗留 running」通路)。
- **建议修法**:executor 关键推进补 expect_stage;driver 层捕获 StageConflict
  转结构化 note(「步骤已被外部终结,本回合让位」),run 状态交给终结者。

### P2-4r2 wsl.state() 把 job.pid 内容未校验插进 root bash(防御纵深)

- **位置**:`runtime/wsl.py:211-221`。
- **问题**:`pid = pid_f.read_text().strip()` 后直接
  `f"awk '{{print $22}}' /proc/{pid}/stat ..."` 进 `bash -lc`(以 root 跑在
  发行版内)。正常内容来自 wrapper 的 `echo $$`(纯数字),但 job.pid 位于
  作业目录 —— 任何能写该目录的进程可注入 `1/stat; <任意命令> #`。与上轮
  P2-8(shell_line 逐字通道)同类,是新增实例。
- **建议修法**:`re.fullmatch(r"\d+", pid)` 不通过按 orphaned/unknown 处置;
  顺带把 `prepare()` 的 env 键名也断言 `[A-Z_][A-Z0-9_]*`。

### P2-5r2 reattach 后端按「引擎+探测」路由,不按作业目录归属

- **位置**:`loop/driver.py:112-128`(`_backend_for`)+
  `runtime/backend_select.py:50-63`;对照已修的 admin 侧
  `backend_for_job_dir`(`backend_select.py:66-78`)。
- **问题**:续跑/接回一个已有 `job_dir` 的步骤时,后端仍靠 `wsl_reachable`
  现场探测决定。探测瞬断(wsl 服务重启)、`INSAR_WSL_DISTRO` 改名、或运维
  强制 `INSAR_JOB_BACKEND=local` 时,WSL 活作业(`\\wsl.localhost` 目录,
  **无 job.hb**,wrapper.sh 不写心跳)会交给 LocalJobBackend 判活 →
  `jobs.py:139-143`「有 pid 无 hb → orphaned」两击即中(约 0.6s)→ run 被
  标 interrupted,Linux 侧进程照跑 —— 正是 FOLLOWUPS #13 在 admin 侧修掉的
  误判,在 driver 接回路径还在。executor 的认领判活(`executor.py:147`)同理。
- **建议修法**:`step.job_dir` 已存在时用 `backend_for_job_dir` 按归属路由
  (POSIX/UNC 前缀 → WSL),只有全新启动才走引擎+探测路由。

### P2-6r2 /api/figures 枚举-读取窗口的 TOCTOU → 单文件消失 500 整表

- **位置**:`api/app.py:567-597`(`entry()` 里 `target.stat()` 与外层
  `is_file()`/`iterdir()` 非原子)。
- **问题**:该端点被画廊 3s 轮询,恰逢出图步骤覆写/清理文件时,
  `is_file()` 通过后 `stat()` 抛 FileNotFoundError → 整个清单 500,
  与 docstring「文件已缺失的行不列」不符。
- **建议修法**:`entry()` 包 `except OSError: continue`(逐行跳过)。

### P2-7r2 符号链/联接在 figures 面上的语义不一致

- **位置**:`api/app.py:539-554`(resolve 全程 `.resolve()` 跟随链接)、
  `592-596`(目录枚举 `iterdir` 会列出指向工作区外的 symlink 成员)、
  `619-627`(file 参数取回时 resolve 越界 → 404);
  `engines/localdata.py:44-53`(local_import 用 `mklink /J` 把外部数据源
  联接进工作区)。
- **问题**:两面性 —— (a) 枚举列出外链成员(名字/大小/mtime 经 `stat()`
  泄漏),点开却 404,画廊出"死图";(b) 反向:凡经目录联接导入的产物树,
  resolve 后落在工作区**外** → 永远 404 —— 今天 figures 都由脚本 mkdir 直写
  不受影响,但任何未来把图件放进联接树(如 HyP3 产品自带 browse PNG)的
  改动会静默失效。
- **建议修法**:枚举时对成员同样 resolve+越界过滤(与取回口径一致);
  对「工作区内联接点」定策略 —— 要么在 resolve 前豁免顶层联接(以联接点
  本身为容器边界),要么文档化"联接树产物不可经 API 直读"。

### P2-8r2 turn 的 next_run 覆写「先消费后校验」:非法覆写被消费即蒸发

- **位置**:`loop/driver.py:186-195`(consume_action 在 make_plan 之前)+
